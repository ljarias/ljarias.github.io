Guía práctica · Bases de Datos

¿No sabes por dónde empezar a documentar tu base de datos?

Una guía para estudiantes que quieren documentar su proyecto sin morir en el intento. Comienza por lo sencillo: entender el problema, explicar las tablas y reunir evidencias. Luego aprende cómo documentar un esquema MySQL o MariaDB, incluso si ya existe.

MySQL / MariaDBIngeniería inversaDiagrama E/RDiccionario de datosEvidencias técnicas

Tu primera ruta: comienza en 5 pasos

No tienes que dominar MySQL ni instalar cuatro programas para comenzar. Trabaja con el enunciado de tu proyecto y reúne estas cinco evidencias:

  1. Entiende el problema: escribe en tus palabras qué quiere resolver la aplicación, quiénes la usan y cuáles son las reglas del negocio.
  2. Identifica las entidades: anota los objetos del problema (por ejemplo, cliente, préstamo, pago) y explica qué información conserva cada uno.
  3. Dibuja las relaciones: define quién depende de quién y si la relación es 1:1, 1:N o N:M. Obtén tu diagrama E/R.
  4. Crea el diccionario: para cada columna escribe nombre, significado, tipo, obligatoriedad y si es PK o FK.
  5. Documenta y comprueba: guarda el DDL comentado, contrasta estructura y diagrama, y prepara un pequeño informe de evidencias.

Tu carpeta mínima: análisis semántico · catálogo de entidades · diagrama · diccionario · DDL · verificaciones. La IA ayuda, pero las decisiones deben ser tuyas.

1. ¿En qué estado está tu base de datos?

Selecciona la ruta que refleje tu situación. Ambas llegan al mismo punto: un esquema de trabajo validado con comentarios técnicos y una documentación externa comprobable. Documentar no equivale a cambiar tablas por cambiar: primero identifica los vacíos y separa documentación de rediseño.

Figura 1. Dos rutas de preparación y una ruta de documentación compartida.

Ruta A · Diseñando

Mi BD no está documentada

Guarda el DDL actual y registra versión, tablas y relaciones.
Identifica descripciones faltantes y confirma su significado con los requisitos del negocio.
Pide a la IA un DDL documentado y una migración solo de comentarios, separados de cualquier propuesta de rediseño.
Si no hay datos, recrea el esquema desde cero solo en ambiente de desarrollo. Si ya existe el esquema, aplica migraciones puntuales en una copia.
Valida que claves, tipos, relaciones y datos (si hay) permanezcan como se espera.
Ir al prompt A
Ruta B · Producción

Mi BD tiene datos y desconozco su documentación

Exporta inventario y DDL real (por ejemplo SHOW CREATE TABLE); comprueba comentarios existentes.
Realiza y verifica un backup, restaura a otra BD o instancia aislada; anonimiza datos personales si se comparten.
Contrasta comentarios existentes con el negocio. Solicita script idempotente o revisable de ALTER TABLE ... COMMENT y MODIFY COLUMN ... COMMENT únicamente para copia.
Revisa especialmente los MODIFY COLUMN: deben reproducir definición completa, nulabilidad, defecto y atributos sin pérdidas.
Ejecuta pruebas y toma evidencias comparativas. La producción no se modifica por esta guía.
Ir al prompt B
Punto de decisión: ¿hay datos que conservar?Si la base está vacía, puedes reconstruirla en desarrollo con DDL documentado. Si tiene datos, no uses DROP DATABASE ni recreación destructiva: genera migraciones no destructivas, respalda y ensaya sobre una restauración. Los comentarios faltantes no justifican modificar restricciones, índices o tipos.

2. Prompts para generar y verificar la documentación interna

Proporciona al asistente el DDL exportado, las reglas conocidas y la versión de MySQL o MariaDB. Los comentarios de negocio deben ser revisados por una persona: la IA no puede deducirlos con certeza a partir de nombres abreviados.

Prompt A · Base en diseño o sin datos

Actúa como DBA experto en MySQL/MariaDB. Estoy DISEÑANDO una base de datos en un entorno de desarrollo.
Motor y versión: [VERSION]. Base: [NOMBRE_BD]. Adjunto DDL y requisitos de negocio.
Objetivo: completar DOCUMENTACIÓN, no cambiar el diseño funcional sin autorización.

1. Inventaría tablas, columnas, PK, FK, UNIQUE, CHECK, DEFAULT, índices, vistas y objetos.
2. Identifica qué tablas y columnas carecen de COMMENT; señala ambigüedades para que yo las confirme.
3. Entrega un DDL COMPLETO documentado para CREAR una BD vacía en desarrollo, conservando
   tipos, longitudes, atributos, restricciones y relaciones originales.
4. Entrega POR SEPARADO un script de migración de solo comentarios para un esquema existente.
5. Separa en un reporte las sugerencias de rediseño: NO las apliques al DDL ni a la migración.
6. Propón verificaciones: SHOW CREATE TABLE, INFORMATION_SCHEMA y comparación antes/después.
7. Nunca incluyas DROP, TRUNCATE ni operaciones sobre registros en la migración.
8. Si falta información semántica, escribe 'PENDIENTE DE CONFIRMAR' y pregunta.

Prompt B · Base en producción con datos

Actúa como DBA y auditor de MySQL/MariaDB. Esta BD está EN PRODUCCIÓN y contiene datos.
Trabajo exclusivamente sobre COPIA RESTAURADA desde backup y nunca sobre producción.
Versión: [VERSION]. BD de prueba: [NOMBRE_COPIA]. Adjunto DDL REAL exportado,
metadatos actuales y requisitos de negocio, sin datos personales ni credenciales.

1. INVENTARIO: identifica comentarios existentes, faltantes y ambiguos, por tabla y columna.
2. Redacta comentarios semánticos concretos; marca cualquier inferencia para aprobación.
3. Genera un archivo SQL de CAMBIOS CONTROLADOS solo para la COPIA:
   - Comentarios de tabla: ALTER TABLE ... COMMENT = '...';
   - Comentarios de columna: usa ALTER TABLE ... MODIFY COLUMN solo si reproduces EXACTAMENTE
     tipo, longitud, UNSIGNED, NULL, DEFAULT, AUTO_INCREMENT, generated columns, charset/collation
     y demás propiedades necesarias; si no puedes garantizarlo, NO generes el cambio.
   - No uses DROP, TRUNCATE, INSERT, DELETE, UPDATE ni cambios a claves, índices o tipos.
4. Organiza el SQL por tablas y explica riesgos y supuestos de cada instrucción.
5. Genera CONSULTAS DE VERIFICACIÓN ANTES/DESPUÉS con INFORMATION_SCHEMA y SHOW CREATE TABLE.
6. Diseña pruebas de conteo de filas, claves, integridad, estructura y rollback mediante restauración.
7. Reporta diferencias esperadas (solo COMMENT) y cualquier cambio inesperado como ERROR.
8. Separa hallazgos de mejora del modelo en un informe NO EJECUTABLE.
9. No asegures que el script es seguro hasta que pase revisión y pruebas reales.

Ejemplo corto · Documentación de una columna

Antes

CREATE TABLE clientes (
 id_cliente INT NOT NULL PRIMARY KEY,
 nombre VARCHAR(100) NOT NULL
);

Después, en DDL para desarrollo

CREATE TABLE clientes (
 id_cliente INT NOT NULL PRIMARY KEY
   COMMENT 'Identificador del cliente',
 nombre VARCHAR(100) NOT NULL
   COMMENT 'Nombre registrado del cliente'
) COMMENT='Personas que compran';
Atención a las migracionesEn MySQL, un MODIFY COLUMN mal construido puede cambiar atributos distintos del comentario. Antes de ejecutar, compara la definición original con la propuesta, revisa dependencias y ensaya en copia. Para un cambio de solo COMMENT de tabla, usa ALTER TABLE nombre COMMENT='...'. Guarda por separado el SQL original y el SQL propuesto.

Consulta útil para comprobar los comentarios antes y después:

SELECT TABLE_NAME, COLUMN_NAME, COLUMN_TYPE,
       IS_NULLABLE, COLUMN_DEFAULT, EXTRA, COLUMN_COMMENT
FROM INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_SCHEMA = '[NOMBRE_BD]'
ORDER BY TABLE_NAME, ORDINAL_POSITION;

Criterios mínimos de calidad documental

CriterioComprobación exigida
Identificación y control de versiónNombre y propósito de la BD, gestor/versión, entorno y fecha; responsable y versión del documento.
Cobertura100 % de tablas y columnas del alcance, tipos exactos, nulabilidad, valores por defecto y comentarios confirmados o marcados como pendientes.
Estructura relacionalModelo E/R legible con PK/FK, cardinalidades contrastadas y relaciones realmente implementadas.
IntegridadPK, FK, UNIQUE, CHECK cuando existen, índices y acciones referenciales documentadas sin inventar restricciones.
Objetos y dependenciasVistas, rutinas, triggers y eventos según existan, con propósito y dependencias conocidas.
Seguridad y privacidadNo exponer contraseñas, datos personales ni copias productivas sin control; minimizar o anonimizar datos de prueba.
VerificabilidadCapturas, exportaciones, consultas SQL de extracción y discrepancias registradas; resultados reproducibles.
MantenibilidadÍndice, glosario, fecha de actualización, ubicación de fuentes y procedimiento para regenerar documentos.
Relación con estándares internacionalesEstos controles están alineados con buenas prácticas de calidad y documentación asociadas a ISO/IEC 25010 (mantenibilidad y calidad del producto), ISO/IEC/IEEE 15289 (contenido de elementos de información del ciclo de vida) e ISO/IEC/IEEE 26514 (documentación para usuarios). No equivalen por sí solos a una certificación ISO, y estas normas no fijan una plantilla universal obligatoria de diccionario SQL.

Propósito de la actividad y producto final

Documentar una base de datos significa construir una explicación verificable de su estructura: qué tablas existen, qué representa cada una, qué columnas contienen, cómo se relacionan, qué restricciones e índices están definidos y qué objetos adicionales forman parte del esquema.

Meta técnica

Leer la base real

La fuente principal es el catálogo de MySQL: INFORMATION_SCHEMA, el DDL que genera el motor y las relaciones que la herramienta detecta.

Meta de evidencia

Demostrar lo encontrado

No basta con afirmar que una PK, FK o índice existe. Debe verse en un diagrama, una tabla de metadatos, el DDL o una captura legible.

Producto esperadoUn paquete ordenado con diagrama E/R, diccionario completo, restricciones, capturas, documentación generada en la herramienta elegida, archivos SQL de documentación (si aplica), y un breve informe de validación de cambios.

2. ¿Qué se debe documentar?

ElementoQué registrarEvidencia recomendada
Base de datosNombre, motor, versión, host/entorno y propósito general.Captura de conexión + SELECT VERSION();
TablasNombre y propósito funcional.Listado del esquema + diccionario.
ColumnasTipo, longitud, NULL/NOT NULL, valor por defecto, clave, extra y comentario si existe.Consulta a INFORMATION_SCHEMA.COLUMNS.
ClavesPK, FK, columnas involucradas y tabla referenciada.Diagrama E/R + reporte de relaciones.
Integridad referencialReglas ON UPDATE y ON DELETE.Consulta de restricciones.
ÍndicesNombre, columnas, unicidad y orden.Consulta a INFORMATION_SCHEMA.STATISTICS.
Objetos adicionalesVistas, triggers, procedimientos y funciones, si existen.Listado de objetos + captura o DDL.
No inventes descripcionesSi la base no tiene comentarios semánticos, puedes redactar una interpretación del propósito de una tabla, pero márcala como “descripción inferida a partir del nombre y relaciones”. No presentes una inferencia como si fuera metadato almacenado.

Flujo común: desde el esquema hacia las evidencias

Figura 2. Tras completar la ruta A o B, se realiza la extracción técnica y la validación de evidencias.

Ruta de generación A: DBeaver Community + consultas de metadatos

Si prefieres una interfaz gráfica, esta es una ruta sencilla: una interfaz gráfica para el diagrama y el editor SQL para extraer el diccionario y las restricciones.

Ventaja para el laboratorioDBeaver permite abrir el diagrama de un esquema existente, reorganizarlo y exportarlo; además, los resultados de una consulta pueden exportarse a formatos como CSV o HTML.

Paso a paso

Instala DBeaver Community desde el enlace oficial de la sección final. Si ya tienes una herramienta equivalente y puedes generar un diagrama y ejecutar SQL, no es obligatorio cambiarla.
Conéctate a la base usando host, puerto, usuario y contraseña. Verifica que ves las tablas correctas. Toma una primera captura donde se reconozca el nombre del esquema, pero oculta contraseñas y datos sensibles.
Genera el diagrama E/R: abre el esquema o el nodo de tablas y usa la pestaña de diagrama. Organiza las tablas para que las relaciones queden legibles. Exporta como PNG.
Ejecuta las consultas de metadatos de la sección 5. Exporta cada resultado como CSV o HTML.
Completa la descripción funcional de las tablas. Esta parte sí requiere análisis: una herramienta puede mostrar la estructura, pero no conoce necesariamente el significado del negocio.
Arma el informe de evidencias con una portada breve, el diagrama, el diccionario y 4–6 capturas clave.

Ruta de generación B: consultas sobre INFORMATION_SCHEMA

MySQL guarda metadatos del esquema en INFORMATION_SCHEMA. Las siguientes consultas son de solo lectura y sirven para crear evidencias directamente desde el motor.

5.1. Identificar motor, versión y base activa

SELECT VERSION() AS version_motor,
       DATABASE() AS base_actual;

5.2. Diccionario de columnas

SELECT
    TABLE_NAME       AS tabla,
    ORDINAL_POSITION AS posicion,
    COLUMN_NAME      AS columna,
    COLUMN_TYPE      AS tipo,
    IS_NULLABLE      AS permite_null,
    COLUMN_DEFAULT   AS valor_default,
    COLUMN_KEY       AS clave,
    EXTRA,
    COLUMN_COMMENT   AS comentario
FROM INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_SCHEMA = DATABASE()
ORDER BY TABLE_NAME, ORDINAL_POSITION;

5.3. Relaciones y reglas de integridad referencial

SELECT
    kcu.TABLE_NAME              AS tabla_hija,
    kcu.COLUMN_NAME             AS columna_fk,
    kcu.CONSTRAINT_NAME         AS restriccion,
    kcu.REFERENCED_TABLE_NAME   AS tabla_padre,
    kcu.REFERENCED_COLUMN_NAME  AS columna_referenciada,
    rc.UPDATE_RULE              AS on_update,
    rc.DELETE_RULE              AS on_delete
FROM INFORMATION_SCHEMA.KEY_COLUMN_USAGE kcu
JOIN INFORMATION_SCHEMA.REFERENTIAL_CONSTRAINTS rc
  ON rc.CONSTRAINT_SCHEMA = kcu.CONSTRAINT_SCHEMA
 AND rc.CONSTRAINT_NAME   = kcu.CONSTRAINT_NAME
 AND rc.TABLE_NAME        = kcu.TABLE_NAME
WHERE kcu.CONSTRAINT_SCHEMA = DATABASE()
  AND kcu.REFERENCED_TABLE_NAME IS NOT NULL
ORDER BY kcu.TABLE_NAME, kcu.CONSTRAINT_NAME, kcu.ORDINAL_POSITION;

5.4. Índices

SELECT
    TABLE_NAME,
    INDEX_NAME,
    CASE WHEN NON_UNIQUE = 0 THEN 'SI' ELSE 'NO' END AS es_unico,
    SEQ_IN_INDEX,
    COLUMN_NAME,
    INDEX_TYPE
FROM INFORMATION_SCHEMA.STATISTICS
WHERE TABLE_SCHEMA = DATABASE()
ORDER BY TABLE_NAME, INDEX_NAME, SEQ_IN_INDEX;

5.5. Objetos adicionales

-- Vistas
SELECT TABLE_NAME AS vista
FROM INFORMATION_SCHEMA.VIEWS
WHERE TABLE_SCHEMA = DATABASE();

-- Triggers
SELECT TRIGGER_NAME, EVENT_MANIPULATION, EVENT_OBJECT_TABLE, ACTION_TIMING
FROM INFORMATION_SCHEMA.TRIGGERS
WHERE TRIGGER_SCHEMA = DATABASE();

-- Procedimientos y funciones
SELECT ROUTINE_NAME, ROUTINE_TYPE
FROM INFORMATION_SCHEMA.ROUTINES
WHERE ROUTINE_SCHEMA = DATABASE();
Importante sobre los comentarios en MySQLMySQL almacena comentarios de tablas y columnas cuando se definen con la opción COMMENT. Para esta actividad no es obligatorio agregarlos a la base si no existen; pueden documentarse externamente en el informe. Evita modificar el esquema solo para “llenar comentarios”.

Ruta de generación C: tbls

tbls genera documentación en Markdown y diagramas a partir de una conexión real. Es útil si se quiere una carpeta de documentación reproducible y fácil de subir a Git.

Úsalo como alternativa, no como requisito adicionalSi el estudiante ya obtuvo un buen diagrama y diccionario con DBeaver/SQL, no necesita repetir todo con tbls. Esta ruta sirve para profundizar en documentación automatizada.

Configuración básica en Windows

Descarga el ZIP para Windows x64 desde Releases, descomprímelo y crea en la misma carpeta un archivo .tbls.yml. Reemplaza los valores entre corchetes.

name: "Documentacion de [NOMBRE_BD]"
dsn: "mysql://[USUARIO]:[PASSWORD]@127.0.0.1:3306/[NOMBRE_BD]"
docPath: "docs_bd"
er:
  format: svg

Si el usuario no tiene contraseña en un entorno local de laboratorio, puede omitirse el segmento :[PASSWORD].

.\tbls.exe doc

La carpeta docs_bd contendrá la documentación del esquema y el diagrama. Conserva como evidencia el README.md, el diagrama y, si se genera, schema.json.

No publiques credencialesSi vas a subir .tbls.yml a un repositorio, no dejes una contraseña real escrita allí. Usa un usuario de solo lectura o variables de entorno.

Ruta de generación D: SchemaSpy

SchemaSpy genera un sitio HTML navegable con tablas, relaciones y diagramas. Es una buena opción cuando se quiere entregar una documentación web completa, aunque su instalación requiere más componentes.

Requisitos

  • Java 17 o superior.
  • Archivo JAR de SchemaSpy.
  • Driver JDBC para MySQL.
  • Para versiones recientes puede usarse -vizjs para renderizar diagramas sin instalar Graphviz.

Ejemplo de ejecución en PowerShell

java -jar .\schemaspy.jar `
  -t mysql `
  -dp .\mysql-connector-j.jar `
  -host 127.0.0.1 `
  -port 3306 `
  -db [NOMBRE_BD] `
  -s [NOMBRE_BD] `
  -u [USUARIO] `
  -p [PASSWORD] `
  -vizjs `
  -o .\reporte_schemaspy

Al terminar, abre reporte_schemaspy\index.html. Esa carpeta completa puede conservarse como evidencia navegable.

Uso responsable de IA para apoyar la documentación

La IA puede ayudar a interpretar el DDL o a redactar descripciones, pero la fuente de verdad debe seguir siendo la base de datos real.

Prompt recomendado: auditoría en modo lecturaEl objetivo del prompt es analizar y explicar, no modificar automáticamente el esquema.
Actúa como analista de bases de datos. Voy a entregarte el DDL exportado de una base MySQL que YA está desplegada.

Tu tarea es SOLO documentar y revisar; no generes ALTER TABLE ni propongas cambios como si ya estuvieran aprobados.

1. Resume el propósito probable de cada tabla.
2. Identifica PK, FK y relaciones.
3. Explica restricciones, índices y valores por defecto.
4. Señala posibles dudas o inconsistencias, pero sepáralas claramente de los hechos observados.
5. Genera un borrador de diccionario de datos en tabla.
6. Marca como "inferencia" cualquier descripción que no esté explícita en COMMENT, nombres o restricciones.

Evidencia 1 · Contexto
Captura del esquema visible en la herramienta y resultado de SELECT VERSION(), DATABASE().
Evidencia 2 · Diagrama E/R
Imagen completa, legible y con nombres de tablas, PK y FK visibles.
Evidencia 3 · Diccionario
Exportación de columnas con tipo, nulabilidad, default, clave y comentario.
Evidencia 4 · Integridad
Listado de FK con tabla padre, columna referenciada, ON UPDATE y ON DELETE.
Evidencia 5 · Índices
Listado de índices y una breve interpretación de los más importantes.
Evidencia 6 · Explicación
Descripción de 5 a 10 tablas principales y de las relaciones más relevantes del sistema.

Lista de verificación antes de entregar

  • El diagrama coincide con las tablas que realmente existen.
  • El diccionario incluye todas las columnas del esquema asignado.
  • Las PK y FK están identificadas correctamente.
  • Las capturas son legibles y no muestran contraseñas.
  • Se distinguen hechos técnicos de interpretaciones o inferencias.
  • El informe explica la estructura; no se limita a pegar capturas.
  • Si se usó IA, la información fue contrastada con la base real.
  • El informe identifica ruta A o B y evidencia backup/restauración cuando corresponda.
  • Se conserva el DDL original, el documentado y las diferencias aprobadas, sin ejecutar cambios destructivos.
